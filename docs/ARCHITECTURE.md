# ARCHITECTURE: Vigil

Version 1.0 · 2026-11-13. Types and function signatures live in `CONTRACTS.md`. If this file and `CONTRACTS.md` disagree on a type or signature, `CONTRACTS.md` wins. If they disagree on algorithm or numbers, this file wins.

## 1. Principles

1. **One language (TypeScript) for engine, app, and harness.** The code that is tested in the harness is exactly the code that runs in the browser.
2. **No backend.** Everything runs in the browser. The harness runs the same engine in Node.
3. **Deterministic and explainable.** Seeded randomness. Rules and statistics only. No LLM at runtime.
4. **Contracts first.** Three people work in parallel against frozen types.
5. **Offline first.** No runtime network calls. Static hosting.
6. **Honest.** Illustrative numbers are labeled. Results come from the harness, never hardcoded.

**Evidence-based vs Illustrative simulator parameters:**
- **Evidence-based (sleep only):** Sleep is the only empirically calibrated indicator in this model. NASA OCHMO-TB-041 and Barger et al. (2014) report ISS actigraphy group means of 6.41 h at baseline assessment, 5.86 h during prelaunch (11 days prior), and 6.09 h in flight (in-flight aggregate SD 0.67 h). The simulator applies a constant in-flight adaptation offset of −0.32 h relative to the 6.41 h baseline. The group SD (0.67 h) provides a realistic daily within-person noise scale.
- **Cardiovascular parameters (HR and BP):** In earlier iterations, illustrative transient offsets were applied; however, empirical findings from NASA's CIRCA investigation documented that 24-hour ambulatory blood pressure and heart rate do not exhibit a generic long-term shift in microgravity (outside day/night circadian phase changes that daily-average telemetry cannot capture). Therefore, the simulator applies NO generic adaptation offset to heart rate or blood pressure (offset 0). They vary strictly according to baseline noise and scenario effect ramps.
- **Illustrative modeling assumptions:** All other population means, between-person standard deviations (`betweenSD`), within-person day-to-day standard deviations (`withinSD`), autocorrelation coefficients ($\phi$), and scenario progression ramps are synthetic illustrative modeling assumptions designed for testing and demo purposes, not clinical or epidemiological predictions.

| Indicator | In-flight mean shift relative to baseline | Evidence base |
|---|---|---|
| sleep_hours | −0.32 in flight relative to the 6.41 h baseline mean | Empirical (NASA OCHMO-TB-041 / Barger et al. 2014) |
| heart_rate | 0 (no generic offset; scenario-driven) | Literature-informed (NASA CIRCA) |
| bp_sys / bp_dia | 0 (no generic offset; scenario-driven) | Literature-informed (NASA CIRCA) |
| all others | 0 | Illustrative assumption |

### 6.3 Randomness (exact)

```ts
export function mulberry32(a: number): () => number {
  return function () {
    a |= 0; a = (a + 0x6d2b79f5) | 0;
    let t = Math.imul(a ^ (a >>> 15), 1 | a);
    t = (t + Math.imul(t ^ (t >>> 7), 61 | t)) ^ t;
    return ((t ^ (t >>> 14)) >>> 0) / 4294967296;
  };
}
export function fnv1a(str: string): number {
  let h = 2166136261;
  for (let i = 0; i < str.length; i++) { h ^= str.charCodeAt(i); h = Math.imul(h, 16777619); }
  return h >>> 0;
}
// Gaussian: Box-Muller using two uniform draws; guard u1 > 0.
```

Each (seed, crewId, indicator) pair gets its own stream: `mulberry32(fnv1a(`${seed}:${crewId}:${indicatorId}`))`. Event randomness uses label `event`. Missing-data randomness uses label `missing`. Never use `Math.random()` in `engine`.

### 6.4 Simulator (exact process)

For each indicator except radiation_dose, for each day `d` from `−29` to `180` (30 preflight days: −29..0; 180 mission days: 1..180):

1. `crewBase = popMean + N(0, betweenSD)` (draw once per crew and indicator, first draw of the stream).
2. AR(1) noise: `n_d = φ·n_{d−1} + sqrt(1 − φ²)·withinSD·ε_d`, `n_start ~ N(0, withinSD²)`.
3. `value = crewBase + empirical sleep-period shift (sleep only) + n_d + effects(d)`.
4. Clip to the table range, round to the indicator decimals.
5. Missingness: each value independently set to `null` with probability 0.02 (stream `missing`). Radiation 0.01.

Radiation: preflight `0.007·(1 + N(0, 0.10))`; mission `rate(setting)·(1 + N(0, 0.08))`, times event multiplier if a solar event is active; clip min 0.

Effects use a ramp: `effect(d) = magnitude × clamp((d − onset) / rampDays, 0, 1)` for `d ≥ onset` and `d ≤ endDay` (or no end). If `endDay` is set, after it the effect decays linearly to 0 over `recoverDays`. Effects are never applied to preflight days (onset ≥ 20).

### 6.6 Detector algorithm (`engine/detector.ts`, `analyze(dataset, upToDay)`)

Constants live in `engine/detectorConfig.ts` (the only place they are defined):

```
CUSUM_K = 0.5          // slack
H_WATCH = 3            // starting value, tunable per 6.9
H_FLAG  = 6            // starting value, tunable per 6.9
Z_CLAMP = 6
PERSIST_WINDOW = 7, PERSIST_MIN_DAYS = 4, PERSIST_Z = 0.75, PERSIST_MIN_OBSERVED = 4
PATTERN_ONSET_GAP = 14
SPIKE_Z = 5
POOR_QUALITY_MISSING_FRACTION = 0.4
BASELINE_MIN_N = 14
RADIATION_WATCH_RATIO = 1.5, RADIATION_FLAG_RATIO = 2.5
```

Steps:

1. **Baseline.** From records with `day ≤ 0`: `median` of non-null values; `sigma = max(1.4826 × MAD, minSigma)`; `n` = count. `baselineReady` = every non-radiation indicator has `n ≥ BASELINE_MIN_N`. If not ready, return statuses `ok`, no findings.
2. **Expected and z.** For mission days `1..upToDay`: `expected = median + phaseOffset(indicator, d)`; `z = (value − expected)/sigma` if value non-null else `null`.
3. **CUSUM** (non-radiation indicators), scanning days in order, with `zc = clamp(z, −6, 6)`:
   - up: `C⁺ = max(0, C⁺ + zc − K)`; down: `C⁻ = max(0, C⁻ − zc − K)`. Null days leave C unchanged.
   - Use up for `up`, down for `down`, both for `both`. `cusum = max` of the used ones.
   - `onsetDay` = the day after the most recent day on which the used C was 0.
4. **Persistence** on day `d`: among the last 7 mission days up to `d`, observed days with `z` in the concern direction at least 0.75 (for `both`, either direction at least 0.75 and consistent in sign for those days) number ≥ 4, and at least 4 days were observed.
5. **Indicator status** on day `d`: `flagged` if `cusum ≥ H_FLAG` and persistent; `watch` if `cusum ≥ H_WATCH` (and not flagged); else `ok`.
6. **Isolated spike**: the latest observed day in the last 2 mission days has `|z| > SPIKE_Z` (unclamped), none of the 3 observed days before it has `|z| > 2`, and the indicator is not persistent.
7. **Data quality**: `missingFractionLast7` = missing days of last 7 mission days / 7; `poor` if `> 0.4`.
8. **Radiation rule**: ratio = value / expectedRate(setting). Status `flagged` if any of the last 3 mission days has ratio > 2.5; `watch` if > 1.5; else `ok`. Cumulative dose is computed by UI/guidance as the sum of non-null values from day 1 to the viewed day (not by the detector).
9. **Adaptation note**: latest observed day ≤ 21, indicator has a nonzero max offset (`PHASE_MAX_OFFSET`, currently only `sleep_hours` with −0.32 h; HR and BP have no generic offset), `|(value − median)/sigma| ≥ 1.5`, and `|z| < 1.5`. Meaning: differs from preflight baseline due to expected operational shift, but matches expected in-flight adaptation offset.
10. **Domain status**: worst status among the domain's indicators (flagged > watch > ok).
11. **Findings** (scan days 1..upToDay in order so `firstFlaggedDay` is the first day of the current uninterrupted run):
    - `persistent_change`: one per indicator with status `flagged` on `upToDay`.
    - `multi_signal_pattern`: active on a day if there are two indicators from two different domains, each with status ≥ `watch` and persistent, whose `onsetDay`s differ by ≤ 14. Members = all such indicators within 14 days of the earliest onset in the cluster.
    - `radiation_event`: radiation status `flagged`.
    - `hard_threshold` with `urgent = true`: latest observed value within the last 2 days has `bp_sys ≥ 180` or `bp_dia ≥ 120` or `glucose < 54`.
    - `isolated_spike`: per rule 6.
    - `data_quality_issue`: per rule 7.
    - `expected_adaptation`: per rule 9.
    - `evidenceStrength`: 1 indicator = low, 2 = moderate, 3 or more = high; one tier lower if any member has poor data quality (minimum low).
12. Return per-indicator `points` for every mission day ≤ upToDay (`day, value, expected, z`) for charts.

**No future data:** a test must assert `analyze(ds, d)` equals `analyze(truncate(ds, d), d)` for several `d`.

### 6.7 Systems compared (`engine/systems/*`)

All return `DailyFlag[]` for mission days 1..180 (`flagged` true means "this system says a problem is present today").

- **vigil**: flagged on day `d` if `analyze(ds, d)` has any finding of kind `persistent_change`, `multi_signal_pattern`, `radiation_event`, or `hard_threshold`.
- **threshold** (typical dashboard, one-day triggers, no baseline): heart_rate > 100 or < 45; bp_sys ≥ 140; bp_dia ≥ 90; body_temp ≥ 38.0; glucose ≥ 126 or < 70; sleep_hours < 5.0; exercise_minutes < 30; mood ≤ 2; stress ≥ 4; energy ≤ 2. Radiation uses the shared rule below.
- **zscore** (statistical alerter): for each non-radiation indicator, mean and SD of the previous 14 days' non-null values (at least 7 values; SD floored at `minSigma`); flagged if `z` beyond 3 in the concern direction (either direction for `both`). One day is enough.
- **Radiation rule** shared by all systems (`radiationRule.ts`): flagged if any of the last 3 mission days has value > 2.5 × expected rate for the setting.
- **isolation forest** (P2 priority, optional): only after everything else is done. Standard algorithm: 100 trees, subsample 64, depth limit ceil(log2(64)) = 6, score `2^(−E[h]/c(64))` with `c(n) = 2(ln(n−1) + 0.5772156649) − 2(n−1)/n`. Do not add a library.

### 6.8 Metrics (`engine/metrics.ts`)

For each scenario and system over seeds 1 to 100:

- **Event window**: `[onsetDay, (endDay ?? 180) + 14]` for each ground-truth event.
- **Detection** (medical events only: physiological_drift, solar_event, acute_illness): `D` = first flagged day within the event window; `delay = D − onsetDay`; `missed` if none.
- **False alarm days**: flagged days outside every event window, plus flagged days inside a non-medical event window (sensor_fault window is `[onsetDay, endDay + 1]`).
- **False episodes**: maximal runs of false alarm days, merging runs separated by 2 or fewer days.
- **falseAlarmsPer100Days** = `100 × total false episodes / total days that were eligible for false alarms`, where eligible days are days outside medical event windows (all 180 days for scenarios without medical events).
- Report: `detectedCount`, `eventCount`, `medianDelayDays` (null if none detected), `falseEpisodes`, `falseAlarmsPer100Days`.

### 6.9 Tuning protocol (prevents tuning on the test set)

1. Tuning seeds: 1000 to 1099, scenario `normal_adaptation` plus `slow_drift`. Evaluation seeds: 1 to 100. Never mix them.
2. Allowed to tune: `H_WATCH`, `H_FLAG`, `PERSIST_*`, `PATTERN_ONSET_GAP`, `CUSUM_K`. Goal: vigil false alarms ≤ 1.0 per 100 days on tuning normal runs while still detecting `slow_drift` in at least 90 percent of tuning runs.
3. Freeze the constants, commit with message `engine: freeze detector config`, then run the evaluation once and commit `results.json`. Record final constants and tuning outcome in `MEMORY.md`.
4. If results look unimpressive, report them honestly. Do not retune on evaluation seeds. (If retuning anyway, retune on tuning seeds only and say so on the Proof page.)

### 6.10 Harness (`scripts/run-harness.ts`)

For scenarios in the order of the table in 6.5, seeds 1..100, `crew-1`, setting `deep_space`: generate, run each system, compute metrics, write `public/data/results.json` (`ResultsFile`, see `CONTRACTS.md`) with 2-space indentation and no timestamps (keeps diffs deterministic). Print a readable summary table. Exit code 1 if any run throws.

### 7.5 Alert card construction (`guidance/alertCards.ts`)

- Input: `AnalysisResult`, `MissionContext`. Output: `AlertCard[]` sorted by severity (urgent, review, watch, info), then by `day` descending. Deterministic ids: `${kind}:${indicators.join('+')}:${firstFlaggedDay}`.
- **observation** (template, plain text): `"{label} has {risen|fallen} from your pre-flight baseline since about day {onsetDay}: {baselineValue} → {recentAvg} {unit} (average of the last 7 days)."` For `multi_signal_pattern`: `"{n} measures have shifted together since about day {earliestOnset}: {labels joined with commas}."`
- **evidence**: one `EvidenceItem` per indicator: text `"{label}: pre-flight {baseline}, last 7 days {avg}, {k} of the last 7 days beyond your usual range."`, `days` = the last 7 observed days. Compute numbers from `analysis.indicators[x].points` and `analysis.baselines`; never invent numbers.
- **uncertainty.tier** = finding `evidenceStrength`. **statement** by tier: low → "Only one measure has changed. This alone cannot show a cause."; moderate → "Two measures have changed together. The cause is still unclear."; high → "Several measures have changed together. A cause cannot be named from this data." If `dataQualityPoor`, append " Some recent readings are missing, which lowers confidence."
- **missingInfo**: from the guidance library entry (`questions`), plus "Missing readings: {labels}" if any indicator has `dataQuality === 'poor'`.
- **nextMeasurements**: from the library entry.
- **recommendedActions**: from the library entry, up to 5, merged and de-duplicated for patterns; each action with `requiresSupply` gets `supplyAvailable = ctx.supplies[supply]`; if unavailable show `alternativeText` instead.
- **escalation**: matrix 7.4 using the card severity and `ctx.setting`.
- **sources**: union of source ids from the used library entries and reference ranges.
- Never produce text that names a disease or a diagnosis.

### 7.6 Wellbeing rules (`guidance/wellbeing.ts`)

`evaluateCheckIn(input)`:
1. If `urgentHelpRequested` → `level: 'urgent'`, escalation level `urgent_now`, message: "Contact your crew medical officer and ground now. You do not have to handle this alone."
2. Else if `mood ≤ 2` and `stress ≥ 4` → `level: 'support'`, message "It looks like today is hard. Here are some steps that may help, and the flight surgeon or behavioral health support can talk it through with you."
3. Else if `mood ≤ 2` or `stress ≥ 4` or `energy ≤ 2` → `level: 'support'`, message "Thank you for checking in. Here are a few steps that may help."
4. Else `level: 'none'`, message "Thanks for checking in."
Suggestions (support level): the library entries `wellbeing:support` (breathing, routine, contact people, exercise). No scores, no labels such as "depressed" or "anxious". Notes are stored on device and never included in alert cards or any export unless the astronaut presses "Share with ground" (stores a flag only; there is no network).

### 7.7 NASA risk coverage map (from the organizer's Risks of Human Spaceflight page)

Use the NASA risk names verbatim only as quoted source titles on the About page. This table is shown there so judges can see exactly what the app covers and what it does not.

| NASA HRP risk (as named on the Risks page) | Coverage in Vigil v1 | How |
|---|---|---|
| Risk of Cardiovascular Adaptations | Covered | Heart rate and blood pressure, domain `cardiovascular` |
| Risk of Inadequate Sleep and Irregular Schedules | Covered | Sleep hours, domain `sleep_recovery` |
| Risk of Reduced Cardiorespiratory and Musculoskeletal Fitness | Covered (adherence only) | Exercise minutes as a countermeasure-adherence indicator; the Risks page says all astronauts exercise to counteract losses in bone density, muscle strength, and heart and blood vessel performance |
| Risk of Spaceflight-Induced Bone Changes | Partly | Exercise adherence as a proxy only; bone density is not measured |
| Risk of Behavioral Changes and Psychiatric Disorders | Covered (self-check only) | Mood, stress, energy check-in; no assessment or screening |
| Risk of Radiation-Induced Cancers | Covered (dose tracking only) | Daily and cumulative dose against the expected rate for the mission setting; no health outcome claims |

| Risk of Inadequate Food and Nutrition | Partly | Blood glucose only; no nutrition tracking in v1 |
| Not covered in v1 | Not covered | Altered Sensorimotor and Vestibular Function; Decompression Sickness; Host-Microorganism Interactions; Hypoxia; Injury and Compromised Performance from Spacewalks; Spaceflight Associated Neuro-ocular Syndrome (SANS); Inadequate Teamwork; Inadequate Systems Operations Support; Injury from Dynamic Loads |

Supporting statements from the organizer resources that the About page and project page may paraphrase (with the source link):
- Longer Moon and Mars missions bring more time in weightlessness, more radiation exposure, longer isolation, increased delays in communication with Earth, and less ability to rely on Earth for emergency medical assistance (CSA science page). This is the evidence for mission-aware escalation and offline operation.

## 8. Appendix A: guidance library (transcribe exactly into `src/guidance/library.ts`; do not add entries without human approval)

Format per key: `actions` (id, text, supply?, alternative?), `questions`, `nextMeasurements`, `sources`. Texts are general wellness steps and must stay non-prescriptive.

**heart_rate:up** (sources: src_hrp_risks, src_general_clinical)
- actions: a1 "Sit quietly for 5 minutes, then repeat the measurement." / a2 "Check recent caffeine, hydration, and exercise, and adjust if needed." / a3 "Write down any symptoms such as dizziness, chest discomfort, or shortness of breath." / a4 "Follow your scheduled exercise and rest plan." 
- questions: "Was the reading taken at rest?" / "Any symptoms such as dizziness or chest discomfort?" / "Any recent change in workload, caffeine, or sleep?"
- nextMeasurements: "Resting heart rate after 5 minutes seated" (supply: wrist_hr_monitor; alternative "Count your pulse for 30 seconds and double it.")

**bp:up** (applies to bp_sys and bp_dia; sources: src_aha_acc_bp, src_hrp_risks)
- actions: a1 "Sit for 5 minutes with your back supported and feet flat, then repeat the reading." (supply: bp_cuff; alternative "Note how you feel and report that a cuff reading is not available.") / a2 "Note recent salt, caffeine, stress, and exercise." / a3 "Record any headache, vision change, or chest discomfort."
- questions: "Was the cuff sized and placed correctly?" / "Any headache or vision change?" / "Any recent change in exercise or diet?"
- nextMeasurements: "Repeat blood pressure after 5 minutes of rest"

**body_temp:up** (sources: src_general_clinical, src_hrp_risks)
- actions: a1 "Repeat the temperature in 15 minutes." (supply: thermometer; alternative "Note how warm or chilled you feel and report that a thermometer is not available.") / a2 "Drink fluids and rest as your schedule allows." / a3 "Record other symptoms such as cough, sore throat, or body aches."
- questions: "Any other symptoms?" / "Has any crew member been unwell?" / "Was the thermometer used correctly?"
- nextMeasurements: "Temperature again in 15 minutes"

**glucose:high** and **glucose:low** (sources: src_ada_glucose)
- high actions: a1 "Confirm the reading was taken fasting, and repeat it." (supply: glucometer; alternative "Report that a glucose meter is not available.") / a2 "Note recent meals, snacks, and stress." / a3 "Record symptoms such as thirst or frequent urination."
- low actions: a1 "Repeat the reading now." (supply: glucometer) / a2 "If you feel shaky or confused, follow your crew medical procedures and tell a crew member." / a3 "Note your last meal and recent exercise."
- questions: "Was the reading fasting?" / "When was the last meal?" / "Any shakiness, sweating, or confusion?"

**sleep_hours:down** (sources: src_aasm_sleep, src_hrp_hazards)
- actions: a1 "Keep a consistent sleep window." / a2 "Reduce bright light and screens before sleep." (alternative "Dim your sleep station lighting.") / a3 "Limit caffeine in the hours before sleep." / a4 "Use a sleep mask and earplugs if available." (supply: sleep_mask; alternative "Cover or dim the light near your sleep station.")
- questions: "Has your sleep schedule shifted?" / "Is noise or light disturbing sleep?" / "Any change in workload or stress?"

**exercise_minutes:down** (sources: src_hrp_hazards, src_hrp_risks)
- actions: a1 "Complete your scheduled exercise session today." (supply: exercise_equipment; alternative "Do body-weight resistance and stretching and report that equipment is not available.") / a2 "Split the session into shorter blocks if time is tight." / a3 "Tell the flight surgeon if pain or fatigue stops you from exercising."
- questions: "Was equipment unavailable or a session skipped?" / "Any pain or unusual fatigue?"

**mood:down**, **stress:up**, **energy:down** → use key `behavioral:support` (sources: src_hrp_hazards, src_hrp_risks)
- actions: a1 "Try slow breathing: in for 4 seconds, out for 6, for 2 minutes." / a2 "Keep a regular daily routine, including meals, exercise, and sleep." / a3 "Talk with a crew member or send a message to someone you trust." / a4 "Tell the flight surgeon or behavioral health support if this continues." 
- questions: "How long has this been going on?" / "Has sleep or workload changed?" / "Would talking with someone help?"

**radiation_event** (sources: src_csa_radiation, src_hrp_hazards)
- actions: a1 "Move to the best-shielded area of the vehicle, following your radiation procedures." / a2 "Limit time outside shielded areas until ground advises." / a3 "Report the dose reading and your location to ground."
- questions: "Is a solar event alert active?" / "Where were you when the reading rose?"

**isolated_spike** (sources: src_general_clinical)
- actions: a1 "Repeat the measurement to confirm." / a2 "Check the sensor placement and device battery." 
- questions: "Was the device placed correctly?" / "Did anything unusual happen at the time of reading?"

**data_quality_issue** (sources: src_hrp_risks)
- actions: a1 "Log the missing measurements when you can." / a2 "Check the device and note why readings were missed."
- questions: "Why were readings missed?"

**wellbeing:support** (used by `evaluateCheckIn`): same four actions as `behavioral:support`.

**Urgent hard thresholds** (bp crisis, glucose below 54): card text uses escalation `urgent_now` and one action: "Follow your emergency medical procedures and contact the crew medical officer now." (sources: src_aha_acc_bp or src_ada_glucose accordingly).

Pattern cards (`multi_signal_pattern`) merge the entries of all member indicators (use `bp:up` for bp_sys/bp_dia, `behavioral:support` for mood/stress/energy) and cap at 5 actions, keeping the first action of each key first.

## 9. Storage specification (`src/storage`, library `idb`)

- Database `vigil-db`, version 1.
- Stores: `entries` (keyPath `key` = `${crewId}:${day}`), `checkins` (keyPath `key` = `${crewId}:${day}`), `log` (keyPath `id`, autoIncrement), `settings` (keyPath `key`).
